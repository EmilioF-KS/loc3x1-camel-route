\begin{abstract}
This document describes a contract-first, BPEL-driven integration sample and its transformation into a Spring + Maven + Camel implementation using local agentic tooling. It clarifies the problem, the original technology stack and artefacts, the proposed agent architecture and information flow, and the expected results. It also defines project organisation and installation scripts required to run the pipeline without mocks, using only real endpoints and data.
\end{abstract}


\section{Problem Statement}
The sample contains SOAP (Simple Object Access Protocol: XML-based messaging protocol for web services) WSDL (Web Services Description Language: XML format describing service interfaces)/XSD (XML Schema Definition: XML format defining data structures) contracts and a BPEL (Business Process Execution Language: XML language for orchestrating web-service workflows) process \emph{(LocationRetrievalLOC3X1Process)} that orchestrates two inbound operations and multiple partner service calls. There is no runnable Java build, no proper server host, and legacy Java snippets are considered non-authoritative. The problem is to translate this into a robust Spring Boot (Java micro-service framework) + Maven (Java build/dependency tool) project with Apache Camel (integration routing engine)/CXF (Java web-service framework), regenerate models and stubs from contracts, implement deterministic mappings that replace BPEL assignments, externalise configuration, and provide contract and integration verification. The transformation must be automated by local agents and verified end-to-end without mocks; integration results depend on live endpoints.

\paragraph*{File types: functions, protocols, and standards}
\begin{itemize}
  \item \textbf{BPEL (Business Process Execution Language)}: Defines executable orchestration of service interactions (picks, onMessage, invoke, assign, fault handlers). It runs on a BPEL engine and coordinates partner links and variables to implement business processes, typically calling SOAP-based services described by WSDL. Common deployment uses HTTP(S) transport and adheres to vendor-specific extensions (e.g., IBM WebSphere styles) while following WS-BPEL principles.
  \item \textbf{WSDL (Web Services Description Language)}: Specifies service contracts, including operations (portTypes), request/response messages, bindings, and service endpoints. In this sample WSDLs are document/literal SOAP with HTTP(S) bindings and include fault definitions. Good practice is alignment with WS-I Basic Profile and consistent namespaces and versions for cross-service compatibility.
  \item \textbf{XSD (XML Schema Definition)}: Provides formal XML type definitions for messages and domain objects used by WSDL services and BPEL variables. XSDs enforce structure and validation, carry namespaces for modularity, and support versioning. The shared SimpleFault.xsd standardises fault payloads across services, enabling consistent error reporting.
\end{itemize}


\section{Project Description}
\subsection{Objectives}
Create an automated, agent-driven translation from BPEL + contracts into a Spring Boot + Maven project using Camel/CXF, with deterministic mappings and centralised fault handling, verified via contract checks and real integration tests.

\subsection{Feasibility and Importance}
Feasibility is high because the assets are contract-first and the BPEL encodes mediation steps. Importance lies in replacing legacy BPEL with modern Java micro-integration while preserving behaviour, improving maintainability, and enabling reproducible automation.

\subsection{Challenges and Fine Points}
IBM-specific BPEL features (BOFactory, SDO) must be mapped to plain JAXB + Spring. Some imports may be missing, and business rule nodes (e.g., fire district checks) require explicit specifications. End-to-end tests depend on live partner endpoints; when unavailable, tests must be reported as blocked, never simulated.

\subsection{Used Technology}
\begin{itemize}
  \item \textbf{Deterministic agents via shell/Python; optional LLM reviewer (Ollama/LangGraph)} — Reproducible, CI-safe automation core with an optional, explainability-only reviewer.
  \item \textbf{Java 17} — Long-term-support JVM release providing modern language features and performance.
  \item \textbf{Maven} — Declarative Java build and dependency-management tool.
  \item \textbf{Spring Boot} — Opinionated micro-service framework for rapid, production-ready Spring applications.
  \item \textbf{Apache Camel} — Enterprise-integration patterns engine for declarative routing and mediation.
  \item \textbf{Apache CXF} — Open-source services framework supporting JAX-WS/JAX-RS and SOAP/REST bindings.
  \item \textbf{JAXB/JAX-WS tooling} — Standard XML binding and web-service stub generation from WSDL/XSD.
  \item \textbf{MapStruct} — Compile-time code generator for type-safe, high-performance object mappings.
  \item \textbf{SLF4J/Logback} — Simple logging façade with fast, configurable log implementation.
  \item \textbf{JUnit} — Ubiquitous testing framework for unit and integration verification.
  \item \textbf{Shell/Python automation drivers} — Portable scripts executed inside the project virtual environment to drive agent workflows.
  \item \textbf{jq/yq} — CLI tools for JSON/YAML processing used by contract discovery and preflight reporting.
  \item \textbf{Docker \/ Docker Compose} — Containerisation of services, clients, orchestration, FastAPI, and optional DB; local multi-service orchestration.
  \item \textbf{CI\/CD (GitHub Actions or Jenkins)} — Deterministic pipeline executing preflight, build, test, packaging, and container publish.
  \item \textbf{Node.js \/ React} — Frontend dashboard for evidence browsing and orchestration controls.
  \item \textbf{Python \/ FastAPI} — Lightweight API for evidence metadata and agent orchestration hooks.
\end{itemize}

\section{Agentic Strategy and Implementation Philosophy}
\subsection{Overview of the Agentic Approach}
The transformation from BPEL-based integration to modern Spring Boot + Camel architecture employs an \emph{agentic strategy} that fundamentally differs from traditional code generation or manual migration approaches. Rather than producing static artefacts that become obsolete when contracts change, this system implements a \textbf{closed-loop, evidence-driven integration layer} that continuously adapts to evolving service landscapes whilst maintaining operational stability and auditability.

The core philosophy centres on \textbf{dynamic resilience over static perfection}. The agentic system prioritises maintaining functional integrations even when partner services change locations, bindings, or schemas, rather than requiring manual intervention for every contract modification. This approach recognises that enterprise integration environments are inherently volatile, with services frequently updated, relocated, or temporarily unavailable.

\subsection{The Closed-Loop Integration Cycle}
The agentic system operates through a continuous seven-phase cycle: \textbf{Discover → Validate → Synthesise → Verify → Harden → Monitor → Adapt}. This cycle ensures that integration behaviour remains consistent whilst the underlying implementation adapts to environmental changes.

Figure \ref{fig:agentic-cycle} illustrates this closed-loop process, showing how each phase feeds into the next whilst maintaining evidence trails for governance and auditability.

\subsubsection{Phase Descriptions}
\begin{itemize}
\item \textbf{Discover}: Continuously scans for changes in WSDL locations, schema versions, endpoint availability, and BPEL process definitions. Uses configurable polling intervals and change detection algorithms.
\item \textbf{Validate}: Performs schema compatibility checks, binding validation, and import resolution. Identifies breaking changes versus compatible extensions.
\item \textbf{Synthesise}: Generates integration artefacts using either static code generation (for stable contracts) or dynamic invocation patterns (for volatile contracts). Chooses strategy based on contract stability metrics.
\item \textbf{Verify}: Executes targeted integration tests against live endpoints, capturing evidence of success or failure. Never uses mocks—blocked tests are reported as such.
\item \textbf{Harden}: Converts proven dynamic integrations into optimised static implementations when stability thresholds are met. Maintains both versions during transition periods.
\item \textbf{Monitor}: Tracks runtime performance, error rates, and availability metrics. Detects degradation patterns that trigger cycle re-entry.
\item \textbf{Adapt}: Adjusts integration strategies based on accumulated evidence. May switch from static to dynamic approaches or activate fallback mechanisms.
\end{itemize}

\subsubsection{Deterministic Core and Reviewer Agent}
The core pipeline is \textbf{deterministic}, repository-aware, and evidence-driven. Planning, scaffolding, build, tests, and evaluation are performed by guarded shell/Python scripts that operate only on explicit artefacts (WSDL/XSD, BPEL, YAML specs), enforce virtual-environment execution, and persist logs and run metadata. This yields reproducibility, auditability, and CI compatibility; no local LLM is required for correctness.

\paragraph{Reviewer/Interpreter (Optional)}
When enabled, a local LLM runs \textit{after} evaluation to interpret artefacts and produce an executive explanation report. Inputs include scaffold/build logs, test results, the agent plan, and route specifications. Outputs are written to `doc/reviewer-report.md` as a plain-English narrative of decisions, evidence chains, and risks. The reviewer never changes code or gates release; it augments explainability only.

\paragraph{Guardrails}
LLM outputs are schema-validated and cross-checked against deterministic artefacts; disagreements are flagged, not auto-applied. The deterministic core remains authoritative regardless of reviewer presence.

\subsubsection{Static Generation Benefits}
\begin{itemize}
\item \textbf{Performance}: Compile-time optimisation eliminates runtime reflection overhead
\item \textbf{Type Safety}: Strong typing catches integration errors at build time
\item \textbf{IDE Support}: Full code completion and refactoring capabilities
\item \textbf{Debugging}: Stack traces reference actual Java classes rather than dynamic proxies
\end{itemize}

\subsubsection{Dynamic Invocation Benefits}
\begin{itemize}
\item \textbf{Adaptability}: Continues functioning when contracts change without recompilation
\item \textbf{Resilience}: Graceful degradation when endpoints become temporarily unavailable
\item \textbf{Discovery}: Automatic detection of new operations or modified schemas
\item \textbf{Fallback}: Can switch between multiple endpoint versions transparently
\end{itemize}

\subsection{Evidence-Driven Hardening Process}
The transition from dynamic to static implementations follows a rigorous \textbf{evidence-driven hardening process} that ensures stability before committing to optimised static code generation.

\subsubsection{Evidence Collection Metrics}
\begin{itemize}
\item \textbf{Contract Stability}: Time since last schema change, frequency of endpoint modifications
\item \textbf{Operational Reliability}: Success rate, response time consistency, availability percentage
\item \textbf{Integration Complexity}: Number of transformations, fault handling requirements, orchestration depth
\item \textbf{Business Criticality}: SLA requirements, transaction volume, downstream dependencies
\end{itemize}

\subsubsection{Hardening Thresholds}
Static generation is triggered when all of the following criteria are met for a continuous period:
\begin{itemize}
\item Contract unchanged for minimum 30 days
\item Endpoint availability exceeding 99.5\%
\item Response time variance below 10\% of baseline
\item Zero import resolution failures
\item Successful integration test rate above 98\%
\end{itemize}

\subsection{Guide: Purpose, Inputs, BPEL, Translation, and Validation}\label{sec:beginner-guide}
\paragraph*{Purpose in plain terms}
This project takes an \textbf{IBM-style BPEL} orchestration and turns it into a \textbf{modern Java implementation} using Spring Boot, Maven, Apache Camel, Apache CXF, and MapStruct. In human terms: we read the original service contracts (WSDL/XSD) and the orchestration logic (BPEL), then generate Java code and routes that behave like the original process, with tests and evidence so you can trust what runs locally.

\paragraph*{What is the input?}
The input is the \texttt{sample/} folder containing:
\begin{itemize}
  \item BPEL: \texttt{sample/LocationRetrievalLOC3X1/LocationRetrievalLOC3X1Process.bpel}
  \item Public WSDL: \texttt{sample/LocationRetrievalLOC3X1B/LocationRetrievalLOC3X1B.wsdl}
  \item Internal/Partner WSDLs: \texttt{sample/LocationRetrievalLOC3X1M/LocationRetrievalLOC3X1M.wsdl}, \texttt{sample/CountryRetrievalCRP10X1/CountryRetrievalCRP10X1.wsdl}, \texttt{sample/StateOrProvinceRetrievalCRP11X1/StateOrProvinceRetrievalCRP11X1.wsdl}
  \item Shared XSDs: \texttt{sample/Schemas/*} and faults in \texttt{sample/PrivateSchemas/SimpleFault.xsd}
\end{itemize}
\textbf{How we dissect it}: we list all WSDL/XSDs (contract inventory), parse the BPEL to extract the inbound operations, partner calls and fault paths, and record types and namespaces referenced by messages.

\paragraph*{Essential BPEL concepts with a micro-example}
BPEL is an \textbf{orchestration language} that describes how a service should \textit{receive} a message, \textit{transform} parts of it, \textit{invoke} other services, and \textit{return} a reply or a fault.  
Below is a \textbf{5-line} excerpt from the real LOC3X1 BPEL file (trimmed for clarity) followed by the matching Java/Camel translation so you can see the same intent in both worlds.

\begin{verbatim}
<!-- 1. BPEL fragment -->
<receive name="receiveLOC3X1B"
         partnerLink="LOC3X1B"
         operation="getLocation"
         variable="locRequest" />
<invoke   name="callCRP11X1"
         partnerLink="CRP11X1"
         operation="getState"
         inputVariable="stateReq"
         outputVariable="stateResp" />

// 2. Camel route fragment
from("cxf:/LOC3X1B?serviceClass=LOC3X1B_Service")
  .to("direct:getLocation")
from("direct:getLocation")
  .bean(StateRequestMapper.class)   // maps locRequest → stateReq
  .to("cxf://http://crp11x1host/crp11x1?serviceClass=CRP11X1_Service")
  .bean(StateResponseMapper.class)  // maps stateResp → next form
\end{verbatim}

\paragraph*{What the nouns mean}
\begin{itemize}
  \item \textbf{Contract (WSDL/XSD)} – an XML file that promises “if you POST \emph{this} XML shape to \emph{this} URL you will get back \emph{that} XML shape”.  
  \item \textbf{Java model} – the POJOs that CXF generates from the XSD; they hold the data so Java code can manipulate it without hand-parsing XML.  
  \item \textbf{CXF} – the library that turns the WSDL contract into a living HTTP endpoint (inbound) or a typed client (outbound).  
  \item \textbf{Configure endpoints} – writing \texttt{application.properties} lines such as\\
  \texttt{loc.camel.cxf.client.crp11x1.address=http://crp11x1host/crp11x1} so the route above knows where to send the request.  
  \item \textbf{Implement mappings} – writing a 3-line MapStruct interface like\\
  \texttt{@Mapper public interface StateRequestMapper \{\\
  \hphantom{....}CRP11X1StateRequest toStateRequest(LOC3X1BLocationRequest src); \}}\\
  which the build turns into Java code that copies \texttt{src.getLocationId()} into \texttt{dest.setStateCode()}.  
\end{itemize}

\paragraph*{In one sentence}  
The BPEL “receive-then-invoke” becomes a Camel “from-then-to” route; the WSDL/XSD contract becomes CXF endpoints plus generated Java models; the BPEL assignment becomes a MapStruct mapper; and you configure the actual partner URL in a properties file instead of hard-coding it in XML.
\textit{How files connect}: the BPEL references partner links bound to WSDL ports; each WSDL references XSD types; the public interface (LOC3X1B) maps to internal (LOC3X1M) via field-level assignments. Dependencies are \textbf{contract-first}: types and operations in WSDL/XSD guide all message shapes.

\paragraph*{Translation at a glance (why and how)}
We translate BPEL intent to \textbf{Camel routes + CXF endpoints} and \textbf{MapStruct mappings}. The sequence:
\begin{enumerate}
  \item \textbf{Discover contracts}: read WSDL/XSD to know operations and message types.\
  \item \textbf{Generate Java models}: use CXF/JAXB to create Java classes/stubs from WSDL/XSD.\
  \item \textbf{Parse BPEL}: derive an orchestration spec (who we call, when, and how faults bubble).\
  \item \textbf{Generate routes}: create Camel routes that mirror receive \textrightarrow{} map \textrightarrow{} invoke partners \textrightarrow{} aggregate reply.\
  \item \textbf{Configure endpoints}: CXF inbound consumer (PAYLOAD) and CXF partner clients (PAYLOAD), with properties for addresses/timeouts/TLS.\
  \item \textbf{Implement mappings}: MapStruct interfaces to convert LOC3X1B request types to LOC3X1M and partner formats; stubs where incomplete.\
  \item \textbf{Build and run}: Maven compiles; Spring Boot exposes inbound BasicService; scripts drive SOAP Ping and capture evidence.\
  \item \textbf{Validate}: unit/integration tests check headers (e.g., \texttt{CxfConstants.OPERATION\_NAME}), route flow, and mapping presence; evidence logged.\
\end{enumerate}
This works because \textbf{Camel} implements enterprise integration patterns (routing, transformation, error handling), \textbf{CXF} binds Java code to SOAP contracts, and \textbf{MapStruct} generates safe, fast field mappings from types — together reproducing the BPEL mediation in maintainable Java.

\paragraph*{Technologies in simple words}
\begin{itemize}
  \item \textbf{Java}: the programming language used for services, clients, routes, and mappers.\
  \item \textbf{Maven}: the build tool; compiles code, runs tests, manages dependencies, and packages JARs.\
  \item \textbf{Spring Boot}: a framework for running services; it starts the inbound CXF service (BasicService).\
  \item \textbf{Apache CXF}: connects Java to SOAP; defines endpoints and clients, marshals/unmarshals XML.\
  \item \textbf{Apache Camel}: the routing engine; defines the orchestration as code (receive, call partners, handle errors).\
  \item \textbf{MapStruct}: auto-generates mapping code between Java types (from WSDL-derived classes).\
  \item \textbf{Python/FastAPI}: small API used to trigger runs and collect evidence for builds/tests/logs.\
\end{itemize}

\paragraph*{Why this translation makes sense}
BPEL describes \textit{intent} (how messages flow). Camel+Cxf+MapStruct describe \textit{implementation} with the same contracts. Using PAYLOAD mode in CXF keeps XML processing efficient and flexible while we incrementally add typed mappers. The outcome is \textbf{transparent, testable}, and \textbf{contract-aligned}.

\paragraph*{Limitations, expectations, realities}
\begin{itemize}
  \item \textbf{Mappings are partial}: some MapStruct mappers are stubs; PAYLOAD routes still work but types may be \texttt{Object} until mappings grow.\
  \item \textbf{Partner endpoints}: addresses/timeouts can be placeholders; live invocation may be blocked in tests without real endpoints.\
  \item \textbf{Faults}: SimpleFault mapping is planned; current placeholder serialises JSON and should be replaced by schema-conformant mapping.\
  \item \textbf{TLS}: optional; configure keystores and truststores in \texttt{application.properties} for secure partners.\
\end{itemize}
\textbf{Expectation}: inbound service runs with SOAP Ping; routes set correct operation headers; tests and evidence report status; partner calls can be stubbed.

\paragraph*{What is needed for success}
\begin{itemize}
  \item A working JDK + Maven; scripts runnable in the virtual environment (\texttt{venv/}).\
  \item Valid WSDL/XSDs under \texttt{sample/}; properties set in \texttt{modules/*/src/main/resources/application.properties}.\
  \item Free local ports and correct CXF servlet mappings; optional TLS configured when required.\
  \item Incremental completion of MapStruct mappers for business-critical fields.\
\end{itemize}

\paragraph*{What is the output and where}
\begin{itemize}
  \item Java sources and compiled JARs for modules (contracts, inbound, orchestration, clients, mappings).\
  \item Generated contract code under \texttt{modules/contracts/target/generated-sources/*}.\
  \item Evidence: logs and summaries under \texttt{tests/results/} and per-run copies under \texttt{uploads/\textless{}run\_id\textgreater{}/results/}.\
\end{itemize}
Outputs are organised by module and by test run so you can trace failures and artefacts.

\paragraph*{How it is validated}
\begin{itemize}
  \item \textbf{Unit tests}: mapper interfaces, header settings, small route fragments.\
  \item \textbf{Integration tests}: end-to-end route execution with partner calls marked blocked when endpoints are unavailable.\
  \item \textbf{Runtime evidence}: SOAP Ping request/response files, inbound logs, client logs.\
  \item \textbf{Codegen logs}: CXF/JAXB output confirming contract coverage.\
\end{itemize}
\textbf{Confidence}: high for inbound service bring-up and route wiring; medium for mapping completeness until stubs are replaced. Users should review outputs for critical fields and configure partners before relying on live calls.

 \paragraph{Where results are saved}
\begin{itemize}
  \item Primary evidence: \texttt{tests/results/logs/*.log},\\
        \texttt{tests/results/html/summary.txt}, mapper and unit test outputs.
  \item Generated contracts codegen: \texttt{modules/contracts/target/\\
        generated-sources/*} with preview logs at \texttt{tests/results/\\
        preflight/contracts-codegen.log}.
  \item Client and inbound evidence: \texttt{tests/results/logs/\\
        inbound-service.out}, \texttt{tests/results/logs/soap-ping.xml},\\
        \texttt{tests/results/logs/soap-ping.response.xml}, and client meta\\
        under \texttt{tests/results/artifacts/clients/}.
  \item Per-run copies when triggered via API: \texttt{uploads/\\
        \textless run\_id\textgreater/results/}.
\end{itemize}

\textbf{Outputs:} \texttt{results/preflight/agent-checks.md}; when using shell preflight also \texttt{results/preflight/smoke.log} and \texttt{results/reports/tooling-report.md}.\\

\paragraph{Step 3: Discover and Validate Contracts} \hfill\\

\textbf{Process:} Discovers \texttt{pom.xml} files and updates \texttt{modules/pom.xml} module list accordingly.\\
\textbf{Outputs:} Corrected parent POM with client submodules (e.g., \texttt{clients/locationretrievalloc3x1mpartner}).\\

\paragraph{Step 5: Generate Contract Code (CXF/JAXB)} \hfill\\

\textbf{Process:} Invokes CXF/JAXB to emit classes under \texttt{modules/contracts/target/generated-sources/*}.\\
\textbf{Outputs:} Generated sources; codegen logs (e.g., \texttt{results/preflight/contracts-codegen.log}).\\
\textbf{Technology:} Apache CXF, JAXB, Maven plugins.

\paragraph{Step 6: Analyse BPEL for Orchestration} \hfill\\
\textbf{What it does:} Interprets BPEL partner links and operations to derive mediation steps.\\
\textbf{Agent/Script:} \texttt{agents/bpel\_agent.py}, \texttt{scripts/analyze\_bpel.py}.\\
\textbf{Inputs:} BPEL files under \texttt{sample/LocationRetrievalLOC3X1/}.\\
\textbf{Process:} Extracts partner links, operations, and message shapes; emits \texttt{orchestration/spec.yaml}.\\
\textbf{Outputs:} \texttt{orchestration/spec.yaml} capturing flow and invocations.\\
\textbf{Technology:} Python, XML parsing, domain mapping.

\paragraph{Step 7: Generate Camel Route Skeletons} \hfill\\
\textbf{What it does:} Produces Apache Camel routes aligned with the orchestration spec.\\
\textbf{Agent/Script:} \texttt{scripts/generate\_routes.py}.\\
\textbf{Inputs:} \texttt{orchestration/spec.yaml}, contract inventory.\\
\textbf{Process:} Generates Java DSL routes (e.g., \texttt{GetLocationList3X1BRoute.java}) and documentation (\texttt{modules/orchestration/ROUTES.md}); optional YAML routes for Gradle subproject (\texttt{loc3x1-camel-route/src/main/resources/loc3x1-routes.yaml}).\\
\textbf{Outputs:} Route classes and mapping stubs (\texttt{direct:map*} routes).\\
\textbf{Technology:} Apache Camel (Java DSL and YAML), Spring Boot integration.

\paragraph{Step 8: Configure CXF Endpoints (PAYLOAD)} \hfill\\
\textbf{What it does:} Wires inbound CXF consumer and partner CXF clients in PAYLOAD mode.\\
\textbf{Agent/Script:} \texttt{modules/orchestration/.../CxfServiceConfig.java}, \texttt{modules/inbound/.../CxfConfig.java}.\\
\textbf{Inputs:} \texttt{modules/orchestration/src/main/resources/application.properties} for addresses and timeouts; optional TLS envs.\\
\textbf{Process:} Defines beans like \texttt{locationretrievalloc3x1bEndpoint} and partner clients (\texttt{stateorprovinceretrievalcrp11x1partnerClient}, etc.), sets \texttt{DataFormat=PAYLOAD}, \texttt{serviceClass=Object.class}, applies \texttt{receiveTimeout}/\texttt{connectionTimeout}.\\
\textbf{Outputs:} Active CXF endpoints in the Camel context; inbound CXF servlet published at \texttt{/services/*} with \texttt{/BasicService}.\\
\textbf{Technology:} Apache CXF, Spring Boot auto-config (servlet), Camel CXF component.

\paragraph{Step 9: Implement Mappings (MapStruct)} \hfill\\
\textbf{What it does:} Defines transformation mappers between request/reply schemas and internal DTOs.\\
\textbf{Agent/Script:} MapStruct interfaces under \texttt{modules/mappings/src/main/java/com/ei/camel/*MapMapper.java}; summary in \texttt{MAPPINGS.md}.\\
\textbf{Inputs:} Schema-derived classes (from Codegen) and domain DTOs.\\
\textbf{Process:} Author \texttt{@Mapper} interfaces with methods like \texttt{Object map(Object source)} (stubs) and targeted field mappings; add unit tests under \texttt{modules/mappings/src/test}.\\
\textbf{Outputs:} Compiled mapper implementations via MapStruct; tests verifying basic mapping expectations.\\
\textbf{Technology:} MapStruct, JUnit, Maven Surefire.

\paragraph{Step 10: Build All Modules} \hfill\\
\textbf{What it does:} Compiles and packages contracts, inbound, orchestration, clients, mappings.\\
\textbf{Agent/Script:} \texttt{scripts/build\_all.sh}; Maven multi-module build via \texttt{modules/pom.xml}.\\
\textbf{Inputs:} Source code and POM hierarchy.\\
\textbf{Process:} Runs \texttt{mvn clean package} across modules; emits JARs under \texttt{modules/*/target}.\\
\textbf{Outputs:} Build artefacts and test reports under \texttt{modules/*/target/surefire-reports}.\\
\textbf{Technology:} Maven, Java 17.

\paragraph{Step 11: Run Inbound Service and SOAP Ping} \hfill\\
\textbf{What it does:} Launches Spring Boot + CXF inbound service and probes WSDL + SOAP Ping.\\
\textbf{Agent/Script:} \texttt{scripts/run\_services.sh}; also exposed via \texttt{scripts/agents/run.py} (\texttt{stage\_services}).\\
\textbf{Inputs:} Inbound JAR (\texttt{modules/inbound/target/inbound-*.jar}); env \texttt{INBOUND\_PORT}.\\
\textbf{Process:} Starts the service, waits for WSDL at \texttt{/services/BasicService?wsdl}, posts a SOAP \texttt{Ping} request via \texttt{curl}.\\
\textbf{Outputs:} \texttt{tests/results/logs/inbound-service.out}, \texttt{soap-ping.xml}, \texttt{soap-ping.response.xml}; log summary.\\
\textbf{Technology:} Spring Boot, CXF servlet, curl.

\paragraph{Step 12: Run Client Demo Against Inbound WSDL} \hfill\\
\textbf{What it does:} Builds and runs a CXF client that invokes \texttt{BasicService.Ping}.\\
\textbf{Agent/Script:} \texttt{scripts/run\_clients.sh}; CXF runner \texttt{com.ei.clients.BasicServiceSoapClientRunner}.\\
\textbf{Inputs:} WSDL URL \texttt{BASIC\_SERVICE\_WSDL}, timeouts \texttt{CLIENT\_CONNECT\_TIMEOUT\_MS}/\texttt{CLIENT\_RECEIVE\_TIMEOUT\_MS}.\\
\textbf{Process:} Builds \texttt{modules/clients/locationretrievalloc3x1b}, ensures inbound service is running, executes \texttt{mvn exec:java} with env overrides.\\
\textbf{Outputs:} \texttt{tests/results/logs/client-run.out}, and meta files under \texttt{tests/results/artifacts/clients/} (request parameters and extracted \texttt{Ping reply}).\\
\textbf{Technology:} Apache CXF dynamic client, Maven Exec Plugin.

\paragraph{Step 13: Integration Tests and Evidence Aggregation} \hfill\\
\textbf{What it does:} Runs integration/unit tests, collects logs and HTML summary.\\
\textbf{Agent/Script:} \texttt{scripts/test\_integrations.sh} (requires \texttt{.venv}); Python \texttt{tests/run\_tests.py --all}.\\
\textbf{Inputs:} Test modules (\texttt{tests/test\_*.py}); optional ordinal map \texttt{tests/ordinal-map.txt}.\\
\textbf{Process:} Discovers tests, executes with verbosity; writes logs to \texttt{tests/results/logs/integration-tests.log}; creates \texttt{tests/results/junit} and \texttt{tests/results/html}.\\
\textbf{Outputs:} JUnit XMLs (when configured), \texttt{summary.txt}, and aggregated logs under \texttt{tests/results/}.\\
\textbf{Technology:} Python unittest, file-based reporting.

\paragraph{Step 14: Evidence API Exposure} \hfill\\
\textbf{What it does:} Serves health/status, evidence summaries, logs, and orchestrates pipeline runs.\\
\textbf{Agent/Script:} FastAPI (\texttt{server/main.py}); helper \texttt{scripts/start\_api.sh}.\\
\textbf{Inputs:} \texttt{tests/results/} directory; env \texttt{ENABLE\_PIPELINE\_RUNS}.\\
\textbf{Process:} Exposes \texttt{/api/summary}, \texttt{/api/logs}, \texttt{/api/logs/\{name\}}, and run endpoints \texttt{/api/run}, \texttt{/api/runs}, \texttt{/api/run/\{id\}/status}, copying run outputs under \texttt{uploads/\textless run\_id\textgreater{}/results}.\\
\textbf{Outputs:} JSON responses containing file tails and summary content; run metadata with metrics.\\
\textbf{Technology:} FastAPI, Uvicorn, CORS, simple run tracking.

\paragraph{Step 15: Packaging and Runtime (Optional)} \hfill\\
\textbf{What it does:} Builds containers for inbound CXF service, Evidence API, and frontend; composes them locally.\\
\textbf{Agent/Script:} \texttt{docker-compose.yml}; \texttt{docker/Dockerfile.inbound} or \texttt{docker/Dockerfile.inbound.runtime}, \texttt{docker/Dockerfile.api}, \texttt{docker/Dockerfile.frontend}.\\
\textbf{Inputs:} Built JARs (host-built or in-image), API server code, frontend bundle; env for addresses/timeouts.\\
\textbf{Process:} Builds images and starts services; healthchecks hit \texttt{/services/BasicService?wsdl} and \texttt{/health}; frontend proxies \texttt{/api/*} to \texttt{api:8001}.\\
\textbf{Outputs:} Running containers: \texttt{camel-route-inbound}, \texttt{camel-route-api}, \texttt{camel-route-frontend}; exposed ports \texttt{8085}, \texttt{8001}, \texttt{8080}.\\
\textbf{Technology:} Docker, Compose, Nginx for static frontend and API proxy.

\paragraph{Step 16: Finalise and Persist Artefacts} \hfill\\
\textbf{What it does:} Consolidates outputs per module and per run, ensuring traceability.\\
\textbf{Agent/Script:} FastAPI run pipeline; \texttt{scripts/agents/run.py} stages (env, plan, contracts, schema, scaffold, bpel, build, services, clients, tests).\\
\textbf{Inputs:} All prior stage outputs.\\
\textbf{Process:} Writes canonical evidence to \texttt{tests/results/}; mirrors into \texttt{uploads/\textless run\_id\textgreater{}/results} for API-served runs; updates run status and metrics.\\
\textbf{Outputs:} Deterministic directory layout with logs, summaries, artefacts, and JARs.\\
\textbf{Technology:} Python orchestration, filesystem IO, Spring Boot/CXF runtime artefacts.
