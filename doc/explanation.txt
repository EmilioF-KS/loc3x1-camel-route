LOC-CAMEL-ROUTE: Agentic Integration Strategy and Execution Flow
===============================================================

1) Overview
- Purpose: Build a resilient, evidence-driven integration layer that can
  discover contracts (WSDL/XSD, BPEL), validate them, synthesize working
  integrations, and harden them into production-grade Java when stable.
- Mindset: Closed-loop cycle “discover → validate → synthesize → verify
  → harden → monitor → adapt”. This avoids brittle builds and enables
  runtime adaptability when contracts or endpoints change.

2) Repository Landmarks
- Contracts and schemas: `sample/` (WSDLs, XSDs, BPEL)
- Maven aggregator: `modules/pom.xml`
- Module configs: `modules/*/pom.xml`
- Agent outputs and governance: `doc/master-plan.txt`, `doc/*.md`
- Scripts: `scripts/*.sh` and `scripts/*.py`

3) Agentic Execution Loop (High Level)
- Discover: Enumerate WSDL/XSD/BPEL, gather namespaces, bindings,
  ports, and import/include graphs.
- Validate: Resolve imports/includes (relative and absolute). Check
  that operations have messages, portTypes, bindings, and services.
- Synthesize: Choose invocation strategy:
  - Dynamic clients (JAX-WS Dispatch/CXF dynamic/Camel CXF payload)
    for variability or incomplete contracts.
  - Static stubs (CXF wsdl2java + JAXB) when contracts are stable.
- Verify: Run targeted tests and probes (no mocks). Record results,
  payloads, and logs.
- Harden: Generate code and integrate only after repeated success. Keep
  overlays minimal; preserve source-of-truth contracts.
- Monitor & Adapt: Observe runtime behaviour, detect drifts, fall back
  to dynamic invocation, re-validate, and propose updates.

| Discover  | -> | Validate | -> | Synthesize | -> | Verify  | -> | Harden  |
+-----------+    +----------+    +------------+    +---------+    +---------+

4) Build & Codegen Flow (What Runs Where)
- Aggregator (`modules/pom.xml`) defines modules, imports BOMs
  (Spring Boot, Camel, CXF), and pluginManagement.
- Contracts module (`modules/contracts/pom.xml`):
  - CXF codegen plugin (`cxf-codegen-plugin`) with `<wsdlOptions>`
    pointing at `sample/...Http.wsdl` for services/ports.
  - Output: Generated sources under
    `modules/contracts/target/generated-sources/cxf/`.
  - Compile dependencies: `jakarta.xml.ws-api`, `jakarta.xml.bind-api`,
    `jaxb-runtime` for generated annotations and JAX-WS types.
- Clients/services/orchestration modules:
  - Consume generated classes (static) or configure dynamic endpoints
    (payload mode) depending on stability.

+--------------------+     +---------------------+     +------------------+
| Parent Aggregator  | --> | Contracts Codegen   | --> | Clients/Services |
| modules/pom.xml    |     | cxf wsdl2java       |     | Camel/CXF        |
+--------------------+     +---------------------+     +------------------+
                                    |                          |
                                    v                          v
                           +----------------+          +------------------+
                           | Generated Java |          | Orchestration    |
                           |  (JAXB/JAX-WS) |          |  Camel Routes    |
                           +----------------+          +------------------+

5) Static vs Dynamic Invocation (Why and When)
- Static (codegen): Strong types and developer ergonomics; best when
  contracts are stable.
- Dynamic (payload/Dispatch/CXF dynamic): Resilient to drift, does not
  require compiled stubs; best for exploration, partial contracts, or
  changing endpoints.
- Strategy: Prefer dynamic first; harden to static only after validation
  and stable coverage.

6) Orchestration from BPEL (How Routes Are Derived)
- Inputs: `sample/LocationRetrievalLOC3X1Process.bpel` + `.map`
  artefacts.
- Agent parses: partner links (LOC3X1M, CRP11X1, CRP10X1), inbound
  ops, invokes, variables, and fault paths.
- Output: `orchestration/spec.yaml` describing flow
  (CRP11X1 → CRP10X1 → LOC3X1M) and mappings.
- Camel routes: Generated from `spec.yaml`, with centralized fault
  handling that serializes `SimpleFault.xsd`.

7) Governance & Evidence
- Governance: British English, no secrets committed, venv-only
  execution.
- Evidence: Logs and reports in `doc/.preflight/`, specs in
  `orchestration/`, inventories in `contracts/`.
- Acceptance: Phase-level criteria defined in `doc/master-plan.txt`
  drive hardening decisions.

10) Flow of Work (Granular Steps)
- Discover: Run inventory scripts
  (`scripts/generate_contract_inventory.py`); produce
  `contracts/inventory.json`.
- Validate: Run `scripts/contracts_validator.py` to check import graphs
  and schema coherence; gather findings.
- Synthesize: Choose dynamic or static per partner; configure CXF
  codegen or dynamic clients accordingly.
- Verify: Execute `mvn -DskipTests package` on modules; inspect
  `doc/.preflight/*.log`; run targeted tests where endpoints exist.
- Harden: When stable, keep codegen enabled, wire routes, and commit
  generated outputs as build artefacts.
- Monitor & Adapt: Instrument services, log faults, and let the agent
  propose changes when drift is detected.

11) Why This Works in Production
- Dynamic fallback ensures continuity when contracts drift.
- Evidence-driven hardening keeps compiled Java aligned with reality.
- Centralized fault handling maintains consistent error surfaces.
- Agents automate discovery, validation, and migration, reducing manual
  patching and brittleness.
